# 02. 아키텍처 설계 (확정)

> 단계 2/4 · 상태: ✅ 확정 · 상위 인덱스: [README.md](README.md) · 선행: [01-기획서.md](01-기획서.md)

기획서(§5)에서 확정한 4단계 기획을 시스템으로 표현하기 위한 아키텍처를 설계한다.
설계 원칙은 **기존 에이전트 빌더 파이프라인을 최대한 재사용**하고, 그 위에
**단계(stage)와 산출물(artifact)** 개념만 얇게 얹는 것이다.

## 1. 설계 원칙

- **재사용 우선**: 세션·프로바이더·컨텍스트 주입·diff 승인 등 검증된 흐름을 다시 만들지 않는다.
- **얇은 계층 추가**: "기획"은 기존 채팅 위에 *단계 상태 + 확정 산출물*을 더한 얇은 오케스트레이션이다.
- **문서가 1급 산출물**: 단계별 결과는 대화 로그가 아니라 확정 가능한 문서(마크다운)로 남긴다.
- **경계 유지**: 코드/자원 접근 방침(중앙 게이트웨이 경유)은 빌더와 동일하게 유지한다.

## 2. 현행(에이전트 빌더) 아키텍처 요약

기획은 아래 현행 흐름의 앞단에 얹힌다. (근거: `app/api/llm.py`, `console/src/pages/Chat.tsx`)

```
사용자
  │  프로젝트·프로바이더·브랜치 선택
  ▼
[console] Chat.tsx ──POST /chat/sessions──▶ [api] create_session
  │                                             └▶ ChatSession(project, provider, branch)
  │  요구사항 입력
  ▼
POST /chat/sessions/{id}/messages ──▶ post_message
  │   ├─ 시스템 프롬프트: Agent Builder mandate + EDIT_SYSTEM_PROMPT
  │   ├─ 컨텍스트 주입: 스택/의존성 · 바인딩 모듈(A2A 카드) · 가용 자원 · 코드 구조
  │   ├─ 도구: MCP tools + A2A tools
  │   └─ llm_service.chat_completion(provider, messages, tools, executor)
  ▼
응답에서 diff 추출 → ProposedChange(proposed)
  │
  ▼
POST /changes/{id}/apply | reject  ──▶ 승인 시 작업 브랜치에 Git 커밋
```

## 3. 목표(에이전트 기획) 아키텍처 (개념)

> 아래는 **설계 개념**이며, 구현은 이번 범위 밖(기획 한정)이다. 구현 착수 시 본 설계를 기준으로 한다.

```
사용자
  │  프로젝트·프로바이더 선택 → 기획 세션 시작
  ▼
[console] AgentPlanning 화면
  │  ┌──────────────────────────────────────────────┐
  │  │ 단계 네비게이터(진행단계 표시)                 │
  │  │  ① 기획서 ─▶ ② 아키텍처 ─▶ ③ 솔루션 ─▶ ④ 개발원칙 │
  │  └──────────────────────────────────────────────┘
  ▼
현재 단계에서 LLM과 대화 (기존 채팅 파이프라인 재사용)
  │   ├─ 시스템 프롬프트: "Agent Planning" + 단계별 지시(stage prompt)
  │   ├─ 컨텍스트 주입: (빌더와 동일) 스택 · 모듈/A2A · 자원 · 코드 구조
  │   │                 + 앞 단계에서 확정된 산출물
  │   └─ 출력: 코드 diff가 아니라 "단계 산출물 문서 초안(마크다운)"
  ▼
사용자 검토·수정 → [확정]
  │   ├─ 산출물(마크다운)을 프로젝트 Gitea 리포 작업 브랜치에 커밋
  │   │     (기존 workspace.apply_diff / ensure_branch 재사용)
  │   └─ PlanArtifact(stage, repo_path, commit_sha, confirmed) 포인터 기록
  ▼
4단계까지 확정 → 기획 세트가 Gitea 리포의 파일로 완성
  │   └─ 개발도구(VSCode·Claude·Antigravity)가 리포 clone/open으로 그대로 열람·활용
  ▼
[외부 빌드] 개발도구에서 구현 (플랫폼 밖) — 상세: §8
  │   ├─ 가용 모듈 제약 문서 = 빌드 guardrail
  │   └─ 플랫폼 MCP 서버 + 내부 모듈 게이트웨이(A2A/프록시)로 연동·모니터링
```

### 핵심 차이 (빌더 → 기획)

| 구분 | 에이전트 빌더(현행) | 에이전트 기획(목표) |
| --- | --- | --- |
| 출력물 | 코드 diff (`ProposedChange`) | 단계 산출물 문서 → **Gitea 리포 파일** |
| 승인 행위 | Git apply / reject | 단계 산출물 확정(confirm) → Gitea 커밋 |
| 진행 개념 | 단일 대화 | **순차 단계 + 진행단계 표시** |
| 컨텍스트 | 스택/모듈/자원/코드 | 좌동 **+ 앞 단계 확정 산출물** |
| LLM 지시 | "코드를 diff로 제안하라" | "이 단계의 문서를 작성하라" |

## 4. 컴포넌트

- **단계 오케스트레이터** — 4단계 순서·현재 단계·확정 상태를 관리. 앞 단계 확정 전
  다음 단계 진입을 막는다(기획서 §5의 "앞 단계 확정 전제").
- **스테이지 프롬프트 세트** — 단계별 시스템 프롬프트. 기존 `EDIT_SYSTEM_PROMPT`(코드 diff 지시)를
  단계별 "문서 작성 지시"로 치환. 컨텍스트 주입 로직(`a2a`, `modules`, `codemap`, `workspace`)은 그대로 사용.
- **산출물 저장소** — 단계별 확정 문서는 **프로젝트 Gitea 리포에 파일로 커밋**(기존 Git
  커밋 인프라 재사용)하고, DB에는 위치/커밋/확정 상태 **포인터**만 둔다. 개발도구는 리포를
  clone/open 해 산출물을 그대로 소비한다. 스키마는
  [04-개발원칙.md §2](04-개발원칙.md#2-스키마-및-의사결정사항)에서 확정.
- **콘솔 기획 화면** — 단계 네비게이터(진행단계 표시)·대화·산출물 미리보기/확정 UI + 외부 빌드 **모니터링** 뷰(§8.4).
- **외부 빌드 연동 표면** — 플랫폼 MCP 서버(제약·모듈 조회, 진행 수신) + 기존 A2A/프록시 게이트웨이 + Gitea 웹훅(§8).

## 5. 데이터 흐름 (단계 전환)

```
[단계 N 진입]
   └─ 컨텍스트 = 공통 컨텍스트(스택/모듈/자원/코드) + Σ(단계 1..N-1 확정 산출물)
   └─ 스테이지 프롬프트(N) 적용
[대화]
   └─ 산출물 초안(마크다운) 생성 · 사용자 수정
[확정]
   └─ 산출물(N) 저장 + confirmed=true
   └─ 단계 N+1 활성화
```

## 6. 비기능 요건

- **보안·권한**: 빌더와 동일. `has('workspace')` 노출, 외부 프로바이더는 admin 키만
  (`_require_admin_for_external`, `app/api/llm.py:41`). 자원 접근은 중앙 게이트웨이 경유 원칙 유지.
- **감사**: 단계 확정 등 주요 행위는 기존 `audit.record` 패턴을 따른다.
- **가용성**: 기획 산출물은 확정 시점에 영속화되어 세션 재접속 시 복원 가능해야 한다
  (현행 빌더는 세션 목록을 localStorage에 보관 — `Chat.tsx:97`).

## 7. 아키텍처 확정 사항

- 기획은 **기존 채팅 파이프라인 위의 얇은 단계 계층**으로 구현한다(신규 LLM 스택 없음).
- 단계별 출력은 **문서 산출물**이며 diff 승인 대신 **확정** 개념을 쓴다.
- 컨텍스트에 **앞 단계 확정 산출물**을 누적 주입한다.
- 확정 산출물은 **프로젝트 Gitea 리포에 커밋**(기존 Git 인프라 재사용)하고, DB에는 포인터만 둔다.
  표준 Git 파일이므로 개발도구(VSCode·Claude·Antigravity) 연동은 별도 어댑터 없이 성립한다.
- **빌드는 외부 개발도구에서 수행**한다. 플랫폼은 빌드를 실행하지 않고, 제약 제공과 모니터링만 한다(§8).
- 구체 스키마·엔드포인트·저장 방식은 [04-개발원칙.md](04-개발원칙.md)에서 확정한다.

## 8. 외부 빌드 연동 및 모니터링

기획 이후 빌드는 플랫폼 밖에서 진행된다([01 §10](01-기획서.md#10-외부-빌드모듈-제약모니터링-요건-확정)).
플랫폼의 책임은 **제약 제공 + 연동 창구 + 모니터링**이며, 셋 다 기존 내부 솔루션을 재사용한다.

### 8.1 경계

```
┌─ 플랫폼(내부) ─────────────────────────────┐        ┌─ 외부 개발도구 ───────────────┐
│ 에이전트 기획 → Gitea 리포(산출물)          │        │ VSCode / Claude / Antigravity │
│ ├ 가용 모듈 제약 문서(솔루션 구성 산출물)    │──clone─▶│  기획 산출물 기반 구현(빌드)   │
│ ├ MCP 서버(제약·모듈 조회 + 진행 수신)       │◀─MCP──▶│  제약 조회 · 진행 보고         │
│ ├ 내부 모듈 게이트웨이(A2A/프록시)           │◀─호출──│  허용된 내부 모듈만 게이트웨이 │
│ └ Gitea push 웹훅(기존) → 진행 신호          │◀─push──│  커밋/푸시                     │
│                    ▼                        │        └───────────────────────────┘
│              모니터링 화면(콘솔)             │
└─────────────────────────────────────────────┘
```

### 8.2 가용 모듈 제약 (guardrail)

- **무엇**: 프로젝트에서 쓸 수 있는 내부 모듈/자원, 각 모듈의 A2A 능력(skills), 주입 환경변수 규약,
  "외부 직접 호출 금지·중앙 게이트웨이 경유" 규칙을 담은 문서.
- **어디서 나오나**: 이는 **3단계(솔루션 구성)의 산출물**이다. 기존 `a2a.list_project_a2a_cards`·
  `modules.available_resources`가 이미 이 정보를 만들므로 그대로 활용한다.
- **어떻게 제약이 되나**: 외부 빌드 도구에 이 문서(및 MCP로 조회 가능한 동일 정보)를 컨텍스트로
  제공해, 목록 밖 자원 사용을 막고 허용 모듈만 규약대로 쓰게 한다(에이전트 빌더의 시스템
  프롬프트 mandate를 문서·MCP로 외부화 — `app/api/llm.py:143`).

### 8.3 연동·모니터링 채널 (기존 인프라 재사용)

| 채널 | 방향 | 재사용 대상 | 용도 |
| --- | --- | --- | --- |
| **MCP 서버** | 외부→플랫폼 | (신규 노출) 기존 A2A/모듈 메타 재사용 | 빌드 도구가 제약·모듈 조회, 진행 보고 |
| A2A/프록시 게이트웨이 | 외부→플랫폼 | `a2a_gateway.py`, `proxy_gateway.py` | 허용된 내부 모듈 실제 호출(경유 강제) |
| Gitea push 웹훅 | 외부→플랫폼 | `app/api/webhooks.py`(기존) | 커밋/푸시를 빌드 진행 신호로 수집 |
| 감사 로그 | 내부 | `audit.record` | MCP·게이트웨이 사용 이력 기록 |

> 플랫폼은 현재 MCP **클라이언트**(`services/mcp_client.py`)다. 외부 빌드 도구(대개 MCP
> 클라이언트)가 붙으려면 플랫폼이 **MCP 서버**를 노출해야 한다 — 이는 신규 능력이며 **설계만**
> 하고 구현은 후속([04 §1.1](04-개발원칙.md#1-구현계획-및-현황관리)). 노출 데이터는 기존 A2A 카드·
> 모듈 메타를 그대로 매핑한다(신규 데이터 소스 없음).

### 8.4 모니터링 화면

- 콘솔 기획 화면에서 세션별 **빌드 진행**을 본다: Gitea 커밋(웹훅), MCP/게이트웨이 사용 이력(감사).
- 별도 CI/러너를 두지 않는다 — 신호원은 위 채널뿐이다(범위 최소화).
