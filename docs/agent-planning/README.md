# 에이전트 기획 (Agent Planning)

기존 **에이전트 빌더**(`/chat`)는 프로젝트·LLM·브랜치를 고르면 곧바로 코드 변경(diff)을
제안·Git 적용하는 "바로 코딩" 흐름이다. 이를 **에이전트 기획**으로 바꿔, 코딩에 들어가기 전
기획 단계를 순차적으로 수행하고 각 단계 산출물을 문서로 확정한다.

> 본 작업 범위는 **기획에 한정**한다. 여기의 문서들은 기능의 설계·의사결정을 확정하기 위한
> 기획 산출물이며, 실제 구현(코드 변경)은 포함하지 않는다.

## 한눈에 보기

- **무엇을** — "바로 코딩"을 "기획 → (이후) 빌드"로 바꿔, 에이전트 코드 생성 전에
  기획서·아키텍처·솔루션 구성·개발원칙을 단계별로 확정하는 기능.
- **왜** — 컨텍스트(모듈/자원/스택)는 이미 주입되지만 곧바로 diff를 만들다 보니 요구사항이
  구조화되지 않은 채 코드가 나온다. 기획 단계를 앞에 두어 재작업을 줄이고, 팀이 검토·승인할
  수 있는 문서 산출물을 남긴다.
- **어떻게(내부 솔루션 재사용)** — 새 LLM 파이프라인을 만들지 않고 기존 채팅 세션·프로바이더·
  모듈/A2A 컨텍스트·diff 승인 인프라를 그대로 재사용한다. 자세한 근거는 [03-솔루션구성.md](03-솔루션구성.md).
- **산출물 저장·연동** — 확정 산출물은 **프로젝트 Gitea 리포에 커밋**되고, 표준 Git 파일이므로
  **VSCode·Claude·Antigravity** 등 개발도구에서 clone/open만으로 열람·활용된다
  ([01 §9](01-기획서.md#9-산출물-저장연동-요건-확정), [03 §3.5](03-솔루션구성.md#35-산출물-저장-및-개발도구-연동-내부-솔루션-기반)).
- **외부 빌드·모니터링** — 빌드(코드 구현)는 **외부 개발도구**에서 수행한다. 플랫폼은 **가용 모듈
  제약 문서**로 guardrail을 주고, **MCP 서버 + A2A/프록시 게이트웨이 + Gitea 웹훅**으로 연동·
  모니터링만 한다([01 §10](01-기획서.md#10-외부-빌드모듈-제약모니터링-요건-확정),
  [02 §8](02-아키텍처설계.md#8-외부-빌드-연동-및-모니터링)).
