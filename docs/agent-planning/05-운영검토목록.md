# 05. 운영 검토 목록

> 상위 인덱스: [README.md](README.md)

빌드를 외주하는 에이전트 팩토리에서 **기능은 동작하지만 운영 단계에서 결정이 필요한 항목**을
모아 둔다. 구현 전 결정이 필요하거나, 운영 데이터를 보고 판단해야 하는 것들이다.
여기 항목이 확정되면 [04-개발원칙.md](04-개발원칙.md) §1.1 구현 표로 옮긴다.

## 1. 추적성 — 기획 ↔ 커밋 ↔ 배포 연결

**현재**: `PlanArtifact.commit_sha`는 산출물 확정 커밋만 가리키고, 외주 빌더의 구현 커밋과는
이어지지 않는다. `BuildTask.commit_sha`가 작업 단위 커밋을 받지만 배포(`Deployment`)와는
연결되지 않는다. 감사 이벤트는 `AuditEvent.target`이 프로젝트 **이름 문자열**이라 세션·작업
단위로 정확히 걸러내지 못한다(`build-status`가 프로젝트 전체 이벤트를 나열하는 이유).

**검토할 것**
- 커밋 메시지·PR 본문에 세션/작업 ID를 심어 한 줄로 추적할지(예: `plan-session: 12, task: 34`).
- `Deployment`에 작업/세션 참조를 추가할지, 아니면 커밋 sha 조인으로 충분한지.
- 감사 이벤트에 구조화된 참조(`session_id`/`task_id`)를 넣을지 — 기존 `detail` JSON으로
  충분한지, 인덱싱 가능한 컬럼이 필요한지.

**결정 필요**: 스키마 변경(마이그레이션) 범위. 지금은 문자열 조회로 버티고 있다.

## 2. 승인·릴리스 게이트 — ✅ 결정: 머지 허용, 위반은 경고

**결정**: 검증 실패가 머지·배포를 막지 않는다. 위반은 **경고로만** 남기고, 고치는 책임은
외주 빌더에게 둔다. 막는 순간 외주 흐름 전체가 멈추는 쪽이 더 큰 비용이라고 판단했다.

**구현된 동작**
- push 웹훅이 배포와 함께 컴플라이언스 검사를 자동 실행한다(`api/webhooks._compliance_task`).
  실패해도 배포를 건드리지 않는다.
- 위반은 감사 이벤트 `plan.build.compliance`(status=warning)로 남고 콘솔 모니터링에 뜬다.
- 외주 빌더는 MCP `list_tasks` 응답 머리에 경고 요약을 함께 받고,
  `check_compliance`로 전문 수정 지시를 받아 스스로 고친다.
- 다시 검사해 깨끗하면 최신 이벤트가 clean이 되어 경고가 자연히 사라진다(별도 해제 절차 없음).

**남은 검토**
- 경고를 무시한 채 릴리스가 반복될 때의 처리(정책 강화 시점).
- 릴리스 승인 주체(사람/자동)와 롤백 기준.

## 3. 비용·쿼터

**현재**: 외주 빌더가 중앙 게이트웨이(`/paas/api/v1/proxy/llm`)로 LLM을 호출하면 토큰 비용은
플랫폼 부담이다. 호출은 감사 로그(`proxy.llm.call`)에 남지만 **사용량·비용 집계와 상한이 없다**.
모듈 프록시(`/proxy/modules/...`)도 마찬가지다.

**검토할 것**
- 집계 단위: 프로젝트별 / 조직별 / 키별. (내부 시스템은 무기한·무제한 접근이라 인증 단에서
  나누기 어렵다 — 호출 시 프로젝트 식별자를 요구할지 결정 필요.)
- 토큰 수를 어디서 얻을지: 프로바이더 응답의 usage 필드를 기록할지, 요청 크기로 근사할지.
- 상한 초과 시 동작: 차단 / 경고 / 관리자 알림.

**결정 필요**: 무제한 접근 정책과 비용 통제는 상충한다. 통제한다면 "차단하지 않고 집계·알림만"이
현재 접근 정책과 충돌하지 않는 선이다.
