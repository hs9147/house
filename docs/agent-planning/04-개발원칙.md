# 04. 개발원칙 (확정)

> 단계 4/4 · 상태: ✅ 확정 · 상위 인덱스: [README.md](README.md) · 선행: [03-솔루션구성.md](03-솔루션구성.md)

앞 세 단계에서 확정한 기획·아키텍처·솔루션 구성을 실제로 이어받을 때의 개발원칙을 정한다.
세 절로 구성한다: **① 구현계획 및 현황관리 · ② 스키마 및 의사결정사항 · ③ 배포 및 사용 가이드.**

> 본 범위는 **기획 한정**이므로, 아래 구현계획/스키마/배포는 **확정된 계획·규격**이며
> 코드 변경은 후속 구현 단계에서 수행한다.

## 2. 스키마 및 의사결정사항

### 2.1 데이터 스키마 (확정안)

**산출물 본문은 프로젝트 Gitea 리포에 파일로 저장**하고([01 §9](01-기획서.md#9-산출물-저장연동-요건-확정)),
DB에는 위치·커밋·확정 상태를 가리키는 **포인터**만 둔다. `ProposedChange`가 diff와 `applied_sha`를
갖는 패턴을 그대로 따른다.

```
PlanArtifact (신설 — 확정안 · 포인터 전용)
  id            PK
  session_id    FK → chat_sessions.id     # 기존 세션 재사용
  stage         Enum(spec, architecture, solution, principles)  # 4단계
  repo_path     String    # Gitea 리포 내 산출물 경로(예: docs/agent-planning/01-기획서.md)
  commit_sha    String?   # 확정 커밋 sha (미확정이면 NULL)
  confirmed     Bool  default False        # 확정 여부
  created_at    DateTime
  (unique: session_id + stage)             # 단계별 1건
```

- **본문 저장소**: 산출물 마크다운 본문은 DB가 아니라 **Gitea 리포**에 커밋된다
  (작업 브랜치는 세션 브랜치 재사용). 초안 편집 중 내용은 대화 로그(`ChatMessage`)에 남고,
  **확정 시점에만** 리포에 커밋되어 `commit_sha`가 채워진다.
- **재사용**: `ChatSession`을 그대로 기획 세션으로 사용한다(신규 세션 테이블 없음).
  커밋은 기존 `workspace.apply_diff`/`ensure_branch`를 사용(신규 저장 인프라 없음).
- **대화 로그**: 단계별 대화는 기존 `ChatMessage`를 재사용(별도 테이블 없음).
- **마이그레이션**: Alembic 신규 리비전 1건(`PlanArtifact` 생성). 기존 테이블 변경 없음 →
  하위 호환 유지. (실행은 후속 구현 단계)
- **가용 모듈 제약 문서**: 별도 테이블을 두지 않는다. `a2a.list_project_a2a_cards`·
  `modules.available_resources` 출력에 게이트웨이 규칙을 더해 **파생 생성**하고, 3단계 산출물로
  Gitea에 커밋한다(원천은 기존 데이터).
- **빌드 모니터링**: 신규 저장소를 두지 않는다. Gitea push 웹훅(`webhooks.py`)과 감사 로그
  (`audit.record`)를 **집계·조회**한다(별도 이벤트 테이블 없음).

### 2.2 API 표면 (확정안, 개념)

기존 `/chat/*` 스타일을 따른다. 실제 시그니처는 구현 시 확정.

- `POST /plan/sessions` — 기획 세션 시작(내부적으로 `ChatSession` 생성).
- `POST /plan/sessions/{id}/stages/{stage}/messages` — 해당 단계 대화(문서 초안 생성).
- `POST /plan/sessions/{id}/stages/{stage}/confirm` — 단계 산출물 확정 → **Gitea 리포에 커밋**하고
  `repo_path`/`commit_sha` 기록.
- `GET /plan/sessions/{id}` — 세션·단계별 산출물/확정 상태 조회(복원·진행단계 표시용).
- `GET /plan/sessions/{id}/repo` — 개발도구 연동용 **리포 clone URL·브랜치·산출물 경로** 반환
  (비관리자에는 기존 정책대로 git_url 마스킹 규칙 적용).
- `GET /plan/projects/{id}/constraints` — **가용 모듈 제약 문서** 조회(A2A 카드·자원 + 게이트웨이
  규칙). 3단계 산출물의 기계가독 원천이며, 외부 빌드의 guardrail 입력이 된다.
- **MCP 서버 엔드포인트**(신규 노출) — 외부 빌드 도구(MCP 클라이언트)가 접속해 제약·모듈을
  조회(`tools/list`·resources)하고 진행을 보고. 노출 데이터는 위 constraints/A2A 카드를 매핑.
- `GET /plan/sessions/{id}/build-status` — 빌드 모니터링용. Gitea 웹훅 커밋 + MCP/게이트웨이
  사용(감사)을 집계해 반환(신규 저장 없이 기존 신호 조회).

## 3. 배포 및 사용 가이드

### 3.1 배포 (구현 이후 적용)

- **기능 플래그**: 에이전트 기획은 기존 `workspace` 모듈에 포함한다(별도 `PAAS_FEATURES` 값
  신설 없음). 비활성 설치본에서는 빌더와 동일하게 메뉴가 숨겨진다(`Layout.tsx`의 `has('workspace')`).
- **마이그레이션**: 배포 시 Alembic 리비전(§2.1) 1건 적용. 롤백은 해당 리비전 downgrade로 처리.
- **무중단**: 스키마 추가는 기존 테이블을 건드리지 않으므로 순차 배포로 충분.
- **설정 변경 없음**: 신규 환경변수·외부 의존성 없음([03 §4](03-솔루션구성.md#4-외부-의존성-정책)).
- **Gitea 전제**: 산출물 저장이 프로젝트 리포에 의존하므로 `PAAS_GITEA_URL`/`PAAS_GITEA_API_TOKEN`이
  설정된 설치본에서 동작한다(미설정 시 기획 세션은 시작되나 확정 커밋 단계에서 안내). Gitea
  구성은 [infra/gitea/README.md](../../infra/gitea/README.md) 참고.
- **MCP 서버 노출**: 외부 빌드 연동을 위해 플랫폼이 MCP 서버 엔드포인트를 노출한다(신규 능력).
  외부 도구가 접근하려면 `PAAS_PLATFORM_PUBLIC_URL`(기존 설정)로 도달 가능해야 한다. 인증은
  기존 API 키 정책을 따른다. 모니터링 신호원인 Gitea 웹훅은 이미 자동 등록된다(`gitea.ensure_webhook`).

### 3.2 사용 가이드 (사용자 관점)

1. 콘솔 좌측 메뉴에서 **에이전트 기획** 선택(`workspace` 활성 설치본).
2. 프로젝트·LLM 프로바이더 선택 후 **기획 세션 시작**.
3. **① 기획서**부터 순서대로:
   - 요구사항을 입력하면 에이전트가 해당 단계 **문서 초안**을 생성.
   - 내용을 검토·수정 후 **확정**하면 다음 단계가 열린다(진행단계 표시로 상태 확인).
4. **② 아키텍처 → ③ 솔루션 구성 → ④ 개발원칙** 순으로 확정.
   - ③ 단계에서 에이전트는 프로젝트에 바인딩된 **내부 모듈/A2A 자원**을 우선 후보로 제시한다.
5. 4단계 확정 완료 시 기획 세트가 완성되며, 이후 빌드 단계 입력으로 활용한다(후속).

**개발도구에서 산출물 열람·활용**

- 각 단계 **확정** 시 산출물이 프로젝트 Gitea 리포(작업 브랜치, 예: `docs/agent-planning/`)에 커밋된다.
- 화면의 **리포 정보**(clone URL·브랜치·경로, `GET /plan/sessions/{id}/repo`)로 원하는 도구에서 연다:
  - **VSCode**: 리포 clone 후 폴더 열기 → 마크다운 편집/프리뷰.
  - **Claude**(Claude Code 등): 클론한 워킹카피를 컨텍스트로 지정해 산출물 참조.
  - **Antigravity**: 리포 기반 IDE에서 동일하게 열람.
- 전용 플러그인 설치는 필요 없다 — 표준 Git 리포의 일반 파일이므로 clone/open만으로 연동된다.

**외부 빌드 및 모니터링**

- **빌드는 외부에서**: 개발도구(VSCode·Claude·Antigravity)에서 리포를 받아 구현한다. 플랫폼은
  빌드를 실행하지 않는다.
- **제약 준수**: 3단계 산출물 **가용 모듈 제약 문서**(및 `GET /plan/projects/{id}/constraints`)를
  빌드 컨텍스트로 제공하면, 허용된 내부 모듈만 게이트웨이 경유로 쓰고 외부 직접 호출은 금지된다.
- **MCP 연동**: MCP를 지원하는 도구(예: Claude Code, Antigravity)는 플랫폼 **MCP 서버**를 등록해
  제약·모듈을 조회하고 진행을 보고한다. 내부 모듈 실제 호출은 A2A/프록시 게이트웨이로 한다.
- **모니터링**: 콘솔 기획 화면의 **빌드 상태** 뷰(`GET /plan/sessions/{id}/build-status`)에서
  외부 빌드의 커밋(Gitea 웹훅)과 모듈 사용 이력(감사)을 확인한다.

### 3.3 운영·감사

- 단계 확정 등 주요 행위는 기존 `audit.record` 패턴으로 감사 로그에 남긴다.
- 외부 LLM 프로바이더 사용은 admin 키 한정 정책을 그대로 적용한다.

## 4. 개발원칙 확정 사항

- 구현은 **P1~P6 순서**로 진행하며 §1.1 표로 현황을 관리한다.
- 스키마는 **`ChatSession` 재사용 + `PlanArtifact`(포인터) 신설**로 최소화하고, 산출물 본문은
  **Gitea 리포에 저장**한다(D7). 하위 호환을 지킨다.
- 개발도구 연동은 **표준 Git 파일**로 성립시키고 도구별 전용 통합은 만들지 않는다(D8).
- **빌드는 외부**에서 수행하고(D9), 플랫폼은 **가용 모듈 제약 문서**(D10)와
  **MCP 서버 + 게이트웨이 + Gitea 웹훅**(D11)으로 제약·연동·모니터링만 담당한다.
- 배포는 신규 인프라·환경변수 없이 마이그레이션 1건으로 충분하며(Gitea·MCP 서버 노출 전제),
  사용 흐름은 §3.2를 표준으로 한다.
- 모든 계획 변경은 문서를 먼저 갱신하고 §2.3 의사결정 로그에 사유를 남긴다.
