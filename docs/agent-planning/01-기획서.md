# 01. 기획서 (확정)

> 단계 1/4 · 상태: ✅ 확정 · 상위 인덱스: [README.md](README.md)

## 1. 배경

`console`의 **에이전트 빌더**(`/chat` → `console/src/pages/Chat.tsx`)는 다음 흐름이다.

1. 프로젝트 + LLM 프로바이더 + 작업 브랜치 선택 → `POST /chat/sessions`
2. 사용자가 요구사항을 입력하면(`POST /chat/sessions/{id}/messages`) 백엔드가
   시스템 프롬프트에 **프로젝트 스택·바인딩된 모듈(A2A 카드)·가용 자원·코드 구조**를
   자동 주입해 LLM을 호출(`app/api/llm.py`).
3. LLM 응답에서 diff를 추출하면 `ProposedChange`로 저장 → 사용자가 **승인(Git apply)**
   또는 **거절**.

즉 **요구사항 입력 → 곧바로 코드 diff**로 이어진다. 컨텍스트 주입 품질은 높지만,
요구사항이 구조화·합의되기 전에 코드가 먼저 나와 다음 문제가 반복된다.

- 무엇을 만들지 합의된 문서가 없다 → 리뷰·승인 근거가 대화 로그뿐.
- 아키텍처/자원 사용 방침을 코드에서 역추적해야 한다.
- 방향이 틀리면 diff 단위로 되돌려야 하고 재작업이 크다.

## 2. 목적

에이전트 빌더를 **에이전트 기획**으로 전환한다. 코드 생성 전에 기획 단계를 순차 수행하고,
각 단계의 결과를 **확정 가능한 문서 산출물**로 남긴다.

- 요구사항을 코드보다 먼저 문서로 확정한다.
- 아키텍처·자원(내부 모듈) 사용 방침을 기획 단계에서 합의한다.
- 산출된 기획 문서가 이후 빌드(코드 생성) 단계의 입력이 된다.

## 3. 범위

### 3.1 In-scope (이번 기획 범위)

- 콘솔 메뉴/화면 표기를 **"에이전트 기획"**으로 정의(기존 "에이전트 빌더" 대체).
- 기획 기능이 수행할 **기획 단계 4개**의 정의·순서·산출물 규격 확정(§5).
- 기존 내부 솔루션(채팅 세션·프로바이더·모듈/A2A 컨텍스트·diff 승인) **재사용 방침** 확정.
- 기획 **산출물의 저장·연동 요건** 확정 — Gitea 저장 및 개발도구 연동(§9).
- **외부 빌드 연동 요건** 확정 — 가용 모듈 제약 문서, MCP·내부 모듈 기반 모니터링(§10).

### 3.2 Out-of-scope (이번 범위 아님 — 후속)

- 실제 코드 구현(백엔드/프런트 변경, 마이그레이션 작성·실행).
- **빌드 실행 자체** — 빌드는 외부 개발도구에서 수행하며 플랫폼이 실행하지 않는다(§10).
  플랫폼이 제공할 MCP 서버·모니터링도 이번엔 **설계만** 하고 구현은 후속.
- 기존 빌더 화면의 물리적 삭제(전환 방식은 §7 의사결정에서 다룸).

## 4. 사용자 & 시나리오

- **주 사용자**: `workspace` 기능이 켜진 설치본에서 프로젝트를 담당하는 개발자/기획자.
  (메뉴는 기존 빌더와 동일하게 `has('workspace')` 조건에서 노출 — `Layout.tsx:63`)
- **대표 시나리오**
  1. 프로젝트·프로바이더 선택 후 **기획 세션** 시작.
  2. 1단계 **기획서**부터 시작해 LLM과 대화하며 각 단계 초안을 생성.
  3. 각 단계 산출물을 검토·수정 후 **확정**하면 다음 단계로 진행.
  4. 4단계까지 확정되면 기획 세트가 완성되어, 이후 빌드 단계 입력으로 전달.

## 5. 기획 단계 정의 (확정)

에이전트 기획은 아래 **4단계**를 순차 수행한다. 각 단계는 앞 단계 확정을 전제로 한다.

| # | 단계 | 이 단계에서 확정하는 것 | 산출물 |
| --- | --- | --- | --- |
| 1 | **기획서 확정** | 요구사항·범위·사용자 시나리오·성공 기준 | 기획서 문서 |
| 2 | **아키텍처 설계** | 컴포넌트·데이터 흐름·경계·비기능 요건 | 아키텍처 문서 |
| 3 | **솔루션 구성** | 사용할 **내부 솔루션**(모듈/A2A/프록시/프로바이더)과 연동 방식 | 솔루션 구성 문서 |
| 4 | **개발원칙** | 구현계획·현황관리, 스키마·의사결정, 배포·사용 가이드 | 개발원칙 문서 |

> 본 문서 집합(`docs/agent-planning/`) 자체가 이 4단계 방법론을 그대로 따라 작성된
> 첫 번째 적용 사례다.

## 6. 성공 기준

- [ ] 4개 기획 단계가 순서·산출물 규격과 함께 문서로 확정된다.
- [ ] 각 단계 문서에 진행 상태(진행단계)가 표시된다.
- [ ] 이후 구현이 시작될 때 별도 재해석 없이 본 기획 문서만으로 착수 가능하다.
- [ ] 내부 솔루션 재사용 방침이 명시되어 신규 인프라 도입이 최소화된다.
- [ ] 확정된 기획 산출물이 **프로젝트 Gitea 리포에 저장**되고, **개발도구(VSCode·Claude·Antigravity 등)에서 열람·활용** 가능하다(§9).
- [ ] **가용 모듈 문서**가 산출되어 외부 빌드의 **제약사항**으로 동작한다(§10).
- [ ] 외부 빌드가 **MCP·내부 모듈 게이트웨이**로 연동되고 플랫폼이 빌드 진행을 **모니터링**할 수 있다(§10).

## 7. 확정 사항 (요약)

- 명칭: **에이전트 기획** (영문 병기 Agent Planning).
- 범위: **기획 한정** — 문서 산출까지. 코드 변경 없음.
- 단계: **기획서 → 아키텍처 → 솔루션 구성 → 개발원칙**(4단계, 순차).
- 전환/명명/보존 등 세부 의사결정은 [04-개발원칙.md §2](04-개발원칙.md#2-스키마-및-의사결정사항)에 로그로 관리.

## 10. 외부 빌드·모듈 제약·모니터링 요건 (확정)

기획 이후 **빌드(코드 구현)는 플랫폼 밖 개발도구에서 수행**한다. 플랫폼은 빌드를 실행하지
않고, 빌드가 **올바른 범위 안에서** 진행되도록 제약을 제공하고 진행을 모니터링한다.

- **빌드는 외부에서 진행**: VSCode·Claude·Antigravity 등에서 기획 산출물(Gitea 리포)을 받아
  구현한다. 기존 "에이전트 빌더"의 플랫폼 내 diff 생성 역할은 외부로 이관된다.
- **가용 모듈 문서 = 빌드 제약**: 프로젝트에서 **사용 가능한 모듈/자원**(바인딩된 내부 모듈·
  A2A 능력·주입 환경변수·중앙 게이트웨이 경유 규칙)을 문서로 산출하고, 이 문서가 외부 빌드의
  **제약사항(guardrail)**으로 동작한다 — 목록에 없는 자원 사용·외부 직접 호출을 금지하고,
  허용된 내부 모듈만 규약대로 쓰게 한다(에이전트 빌더의 보안·아키텍처 mandate를 외부로 이관).
- **내부 모듈·MCP로 빌드 모니터링**: 외부 빌드는 플랫폼이 노출하는 **MCP 서버**와 **내부 모듈
  게이트웨이(A2A/프록시)**로 연동된다. 이를 통해 (a) 빌드 도구가 제약·모듈을 조회하고,
  (b) 플랫폼이 빌드 진행(커밋·도구 사용)을 **모니터링**한다. Gitea push 웹훅(기존)도 모니터링
  신호로 함께 쓴다.

세부 설계는 [02 §8](02-아키텍처설계.md#8-외부-빌드-연동-및-모니터링), 스키마·API·의사결정은
[04 §2](04-개발원칙.md#2-스키마-및-의사결정사항).

## 9. 산출물 저장·연동 요건 (확정)

기획 산출물은 세션에만 머무르지 않고, 이후 개발 단계에서 그대로 쓰이도록 다음을 만족한다.

- **저장소 = 프로젝트 Gitea 리포**: 확정된 각 단계 산출물(마크다운)은 해당 프로젝트의
  Gitea 리포지토리에 파일로 커밋된다. 플랫폼은 이미 조직→Gitea Organization, 프로젝트→리포를
  자동 생성하고(`app/services/gitea.py`) diff 승인 시 작업 브랜치에 커밋하므로
  (`workspace.apply_diff`), **기존 Git 저장·커밋 인프라를 그대로 재사용**한다.
- **표준 위치·형식**: 산출물은 리포 내 약속된 경로(예: `docs/agent-planning/`)에 일반
  마크다운 파일로 둔다. 특수 포맷·전용 뷰어가 필요 없다.
- **개발도구 연동**: 산출물이 표준 Git 리포의 일반 파일이므로, 리포를 clone/open 하는 어떤
  개발도구든 별도 어댑터 없이 열람·편집·참조할 수 있다 — **VSCode**(리포 열기),
  **Claude**(Claude Code 등, 워킹카피 컨텍스트), **Antigravity**(리포 기반 IDE) 등.
  연동의 핵심은 "산출물을 표준 Git 파일로 둔다"이며, 도구별 전용 통합은 만들지 않는다.
- **접근·권한**: Gitea 리포 접근 권한(조직/프로젝트)과 기존 정책을 그대로 따른다. 세부 규격은
  [04-개발원칙.md §2](04-개발원칙.md#2-스키마-및-의사결정사항).
