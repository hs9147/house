# 03. 솔루션 구성 — 내부 솔루션 사용 (확정)

> 단계 3/4 · 상태: ✅ 확정 · 상위 인덱스: [README.md](README.md) · 선행: [02-아키텍처설계.md](02-아키텍처설계.md)

아키텍처(§1 재사용 우선)를 실현하기 위해 **어떤 내부 솔루션을 그대로 쓰고, 무엇만 새로 얹는지**를 확정한다.
원칙: **신규 외부 의존성·신규 인프라 도입 없음.** 플랫폼에 이미 있는 구성요소를 재사용한다.

## 1. 재사용하는 내부 솔루션 (그대로 사용)

| 내부 솔루션 | 위치 | 기획에서의 역할 | 변경 |
| --- | --- | --- | --- |
| 채팅 세션 | `ChatSession` / `app/api/llm.py` `create_session` | 기획 세션의 기반(프로젝트·프로바이더·브랜치) | 없음(재사용) |
| LLM 프로바이더 | `LlmProvider` / `llm_service.chat_completion` | 단계별 대화 수행. 내부/외부 통일 인터페이스 | 없음(재사용) |
| 컨텍스트 주입 | `a2a.list_project_a2a_cards`, `modules.available_resources`, `codemap`, `workspace.detect_project_stack_and_deps` | 단계 대화에 스택/모듈/자원/코드 구조 주입 | 없음(재사용) |
| 모듈·A2A 카드 | `app/services/a2a.py`, `app/services/modules.py` | "내부 솔루션 목록"을 기획 근거로 제공 + **가용 모듈 제약 문서**의 원천 | 없음(재사용) |
| A2A/프록시 게이트웨이(엔드포인트) | `app/api/a2a_gateway.py`, `proxy_gateway.py` | 외부 빌드가 허용된 내부 모듈을 **경유 호출**하는 창구 | 없음(재사용) |
| Gitea push 웹훅 | `app/api/webhooks.py` | 외부 빌드 커밋을 **모니터링 신호**로 수집 | 없음(재사용) |
| 프록시 게이트웨이 방침 | `app/api/proxy_gateway.py`, `a2a_gateway.py` | 자원 접근은 중앙 게이트웨이 경유 — 기획 산출물에 방침으로 반영 | 없음(방침 계승) |
| **Gitea 저장소** | `app/services/gitea.py`, `app/services/workspace.py` | 확정 산출물을 프로젝트 리포에 커밋해 저장. 조직/리포 자동 생성·커밋 인프라 재사용 | 없음(재사용) |
| 감사 로그 | `app/audit.py` `audit.record` | 단계 확정 등 행위 감사 | 없음(패턴 재사용) |
| 콘솔 공통 컴포넌트 | `console/src/components` (`Async`, `StatusPill` 등), `lib/api`, `lib/hooks` | 기획 화면 구성 | 없음(재사용) |

## 2. 새로 얹는 얇은 계층 (신규 최소 요소)

아키텍처 §4의 컴포넌트에 대응한다. **모두 기존 요소 위의 얇은 층**이며 새 인프라가 아니다.

| 신규 요소 | 성격 | 기존 대응 | 비고 |
| --- | --- | --- | --- |
| 스테이지 프롬프트 세트 | 프롬프트 상수 | `llm_service.EDIT_SYSTEM_PROMPT`(코드 diff 지시) | 단계별 "문서 작성 지시"로 치환 |
| 단계 오케스트레이션 | 상태(현재 단계/확정 여부) 관리 | 없음 | 4단계 순서·전제 강제 |
| 산출물 저장(포인터) | Gitea 커밋 결과의 위치/상태 기록 | `ProposedChange`(diff·`applied_sha` 저장) 패턴 참고 | 본문은 Gitea, DB는 포인터. 스키마는 [04 §2](04-개발원칙.md#2-스키마-및-의사결정사항) |
| 기획 화면 | 단계 네비게이터 + 대화 + 산출물 확정 + 빌드 모니터링 뷰 | `Chat.tsx` | 진행단계 표시 UI 포함 |
| 가용 모듈 제약 문서 | 3단계 산출물(문서) | `a2a.list_project_a2a_cards`/`modules.available_resources` 출력 | 기존 데이터를 제약 문서로 정형화 |
| **MCP 서버** | 신규 노출 엔드포인트 | 기존 MCP **클라이언트**(`mcp_client.py`)와 반대 방향 | 외부 빌드 도구가 제약·모듈 조회, 진행 보고 |

## 3. "내부 솔루션 사용"의 이중 의미

본 기능에서 "내부 솔루션 사용"은 두 층위에서 동시에 성립한다.

1. **기능을 만드는 방식** — 위 §1처럼 플랫폼 내부 컴포넌트를 재사용해 에이전트 기획을 구성한다.
2. **기획이 권고하는 방식** — 기획 산출물이 대상 프로젝트에 권고하는 자원 사용도 **내부 모듈/A2A/
   프록시 게이트웨이 우선**을 따른다. 즉 3단계(솔루션 구성)에서 에이전트는 프로젝트에 바인딩된
   내부 모듈(A2A 카드)을 우선 후보로 제시하고, 외부 직접 호출 대신 중앙 게이트웨이 경유를 권고한다
   (에이전트 빌더의 보안·아키텍처 mandate 계승 — `app/api/llm.py:143`).

## 3.5 산출물 저장 및 개발도구 연동 (내부 솔루션 기반)

기획서 §9 요건을 내부 솔루션 재사용만으로 충족한다.

- **저장 = 프로젝트 Gitea 리포**: 확정 산출물(마크다운)을 리포 내 약속 경로
  (예: `docs/agent-planning/`)에 커밋한다. 조직→Gitea Organization, 프로젝트→리포는
  이미 플랫폼이 자동 관리하고(`gitea.ensure_org`/`ensure_repo`), 작업 브랜치 커밋도
  기존 `workspace.apply_diff`/`ensure_branch`가 처리하므로 신규 저장 인프라가 없다.
- **개발도구 연동은 "표준 Git 파일"로 성립**: 산출물이 전용 포맷이 아니라 리포의 일반
  파일이므로, 리포를 clone/open 하는 도구는 어댑터 없이 열람·편집·참조한다.
  - **VSCode** — 리포 열기(clone) 후 마크다운 그대로 편집/프리뷰.
  - **Claude** — Claude Code 등에서 워킹카피를 컨텍스트로 사용(리포 기반).
  - **Antigravity** — 리포 기반 IDE에서 동일하게 열람·활용.
- **도구별 전용 통합 없음**: 연동의 단일 접점은 Gitea 리포다. 특정 도구에 종속되는 플러그인·
  익스텐션·API는 만들지 않는다(범위 밖). 필요 시 API가 리포 clone URL·브랜치·산출물 경로를
  제공해 도구가 바로 열 수 있게 한다.

## 3.6 외부 빌드 연동·모니터링 (내부 솔루션 재사용)

빌드는 외부 개발도구에서 수행되고([01 §10](01-기획서.md#10-외부-빌드모듈-제약모니터링-요건-확정),
[02 §8](02-아키텍처설계.md#8-외부-빌드-연동-및-모니터링)), 플랫폼은 제약·연동·모니터링만 맡는다.
셋 다 기존 자산을 재사용한다.

- **가용 모듈 제약 문서(guardrail)** — 3단계(솔루션 구성)에서 산출. 원천 데이터는 이미 존재하는
  `a2a.list_project_a2a_cards`(모듈→A2A 카드: 능력·엔드포인트·env_prefix)와
  `modules.available_resources`(가용 자원·헬스). 여기에 "외부 직접 호출 금지·중앙 게이트웨이
  경유" 규칙(에이전트 빌더 mandate, `app/api/llm.py:143`)을 더해 **빌드 제약 문서**로 정형화한다.
- **연동 창구** — 외부 빌드는 허용된 내부 모듈을 **A2A/프록시 게이트웨이**로만 호출한다
  (`a2a_gateway.py`/`proxy_gateway.py` 재사용). 제약·모듈 메타 조회와 진행 보고는 플랫폼이
  노출할 **MCP 서버**로 한다.
- **MCP 방향 주의** — 플랫폼은 현재 MCP **클라이언트**다(`mcp_client.py`가 외부 MCP 서버를 소비).
  외부 빌드 도구(MCP 클라이언트)가 붙으려면 플랫폼이 **MCP 서버**를 노출해야 하며, 이는 유일한
  신규 능력이다. 노출 데이터는 기존 A2A 카드·모듈 메타를 매핑하므로 신규 데이터 소스는 없다.
  (본 범위는 설계까지 — 구현은 후속)
- **모니터링 신호** — Gitea push 웹훅(`webhooks.py`, 기존)으로 외부 빌드 커밋을 수집하고,
  MCP·게이트웨이 사용은 `audit.record`로 남겨 콘솔에서 진행을 본다. 별도 CI/러너는 두지 않는다.

## 4. 외부 의존성 정책

- 신규 외부 라이브러리·서비스 **도입 없음**. LLM 호출은 기존 프로바이더 추상화만 사용.
- 외부 LLM 프로바이더 사용은 기존 정책대로 **admin 키 한정**(`_require_admin_for_external`).

## 5. 솔루션 구성 확정 사항

- 에이전트 기획은 **기존 내부 솔루션 재사용 + 얇은 단계/산출물 계층**으로 구성한다.
- 산출물은 **Gitea 리포에 저장**하고(§3.5), 개발도구 연동은 **표준 Git 파일**로 성립시킨다 —
  도구별 전용 통합은 만들지 않는다.
- **빌드는 외부에서** 수행하고, 플랫폼은 **가용 모듈 제약 문서**(3단계 산출물)로 guardrail을
  제공하며, **MCP 서버 + 게이트웨이 + Gitea 웹훅**으로 연동·모니터링한다(§3.6). 유일한 신규 능력은
  **MCP 서버 노출**이며 데이터는 기존 A2A/모듈 메타를 재사용한다.
- 신규 인프라·외부 의존성은 도입하지 않는다.
- 자원 접근·보안 방침(중앙 게이트웨이 경유, 외부 프로바이더 admin 한정)은 빌더에서 그대로 계승한다.
- 다음 단계(개발원칙)에서 이 구성을 전제로 구현계획·스키마·배포/사용 가이드를 확정한다.
