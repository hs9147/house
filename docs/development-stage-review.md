# 개발 단계 신설 전 검토 — 여러 사람이 git을 공유하며 Claude로 개발할 때

작성: 2026-10-28 · 상태: 검토(구현 전)

## 배경과 문제

에이전트 기획(①기획서 ~ ⑤작업 지시) 다음에 **개발 단계**를 신설하려 한다. 개발 단계에서는 여러 사람이 한 프로젝트
리포를 공유하고 각자 Claude로 코드를 고친다. 여러 사람이 쓰므로 정제되지 않은 요청, 서로 상충하는 요청이 들어온다.

- 요청을 **바로 반영하면** 코드가 여러 갈래로 갈린다.
- 반영하기 전에 **확정하려 하면** 결정이 오래 걸린다.

## 결론

요청을 바로 코드로 옮기지 않고 **개발 항목**을 거치게 한다. 항목마다 범위(어느 코드에 닿는지)와 성격(기획 안인지
밖인지)을 먼저 정한 뒤 구현한다. 상충하는 요구의 갈림은 **브랜치가 아니라 설정 스위치(기능 플래그)에** 둔다 — 코드는
한 줄기로 남고, 결정은 스위치 하나를 고르는 일로 작아진다.

## 1. 개발 단계에서 갈림이 생기는 경로

1. **사람별·요청별 브랜치가 오래 산다.** A의 Claude와 B의 Claude가 같은 화면을 다른 방향으로 고치고, 머지 시점에야
   부딪친다.
2. **요청의 성격이 섞인다.** 기획대로 고치는 일(버그·누락)과 기획을 바꾸는 일(동작·범위 변경)이 같은 길로 들어와,
   코드가 기획 문서와 어긋나며 갈라진다.
3. **Claude가 모호한 요청을 그럴듯하게 채운다.** 상충하는 두 요청을 각각 "해석해서" 구현하면 갈림이 코드 안에 숨는다.
4. **같은 일을 두 번 한다.** 지금 작업 지시(BuildTask)에는 담당자·선점이 없어 두 Claude가 같은 항목을 구현할 수 있다.

## 2. 권하는 구조

```
 요청(누구나 · 날것)
   │
   ▼
 개발 항목 ─ 정제(LLM): 재현·완료 기준·닿는 코드(codemap)·성격 판정
   │          진행 중인 항목과 겹침(같은 파일·모듈), 확정 기획과 어긋남 검사
   ├─ 기획 안(버그·누락·구현) ─────────────────── 빠른 길: 결정 없이 바로 준비됨
   ├─ 기획 밖(동작·범위 변경) ─ 결정권자 승인 ── 승인되면 기획 문서도 같이 고친다
   └─ 상충(다른 항목·결정과 부딪침) ─ 결정 대기(기한·기본값)
          └ 급하면 둘 다 플래그 뒤에 구현해 ~dev에서 비교 → 결정 = 스위치 고르기
   ▼
 구현: 항목 하나 = 사람·Claude 하나(선점) = 짧은 브랜치 하나
   Claude는 항목의 완료 기준만 구현하고, 범위를 넘거나 모호하면 멈추고 질의한다
   ▼
 반영: 검사 통과 → 순서대로 머지(기본 브랜치를 늘 배포 가능하게)
   기획 안은 자동 머지 가능, 기획 밖은 결정권자 승인
```

### 2.1 코드가 갈리지 않게

- **트렁크 기반.** 사람별 장기 브랜치를 두지 않는다. 항목 브랜치는 짧게(하루 단위) 끝내고 바로 기본 브랜치에 넣는다.
- **겹침을 미리 안다.** 정제 때 닿는 파일·모듈을 적고(services/codemap), 진행 중인 다른 항목과 겹치면 착수 전에 알려
  순서를 정하거나 합친다.
- **선점(claim).** 한 항목은 한 명만 잡는다. MCP에 `claim_task`를 두어 Claude도 잡은 뒤에만 구현한다.
- **머지 순서.** 동시에 끝난 항목은 하나씩 최신 기본 브랜치 위에 다시 올려 검사한 뒤 넣는다 — 둘 다 통과했는데 합치면
  깨지는 일을 막는다.

### 2.2 결정을 빠르게

- **결정할 일 자체를 줄인다.** 성격 판정에서 기획 안 항목은 결정 없이 간다 — 대부분의 요청이 여기에 들게 하는 것이 목표다.
- **기능 플래그.** 상충하는 동작을 브랜치로 나누지 않고 플래그 뒤에 둘 다 넣어, ~dev에서 바로 비교한다. 결정이 나면 진 쪽
  코드를 지우는 정리 항목을 자동으로 만든다(플래그가 쌓이지 않게). 데이터 구조처럼 플래그로 나눌 수 없는 것만 결정을 기다린다.
- **기한과 기본값.** 결정 대기 항목은 기한을 넘기면 기본값(현행 유지)으로 닫고 기록한다 — 나중에 뒤집을 수 있다.
- **되돌릴 수 있는 결정은 빨리, 되돌리기 어려운 결정(데이터 구조·외부 계약)만 신중히.** LLM이 항목에 이 구분을 표시한다.
- **비교 자료는 LLM이 준비한다.** 상충하는 요청 원문·요청자·시점, 선택지마다 닿는 코드와 기획 문서 범위.

### 2.3 Claude에게 주는 규칙(리포의 개발원칙 문서·MCP 응답)

- 잡은 항목의 완료 기준만 구현한다. 범위 밖 수정은 새 항목으로 제안한다.
- 요청이 모호하거나 다른 항목·결정과 부딪치면 구현하지 않고 질의한다 — 질의는 그 항목의 요청자·결정권자에게 간다.
- 커밋에 항목 번호를 남긴다(지금의 `task #N` 규약).

### 2.4 역할

| 역할 | 하는 일 |
|---|---|
| 요청자 | 요청을 넣고, 질의에 답한다 |
| 결정권자(프로젝트 주인 또는 영역별) | 기획 밖·상충 항목을 승인·결정한다 |
| 구현자(사람 + Claude) | 항목을 선점해 구현하고 완료를 보고한다 |

## 3. 지금 코드 — 쓸 수 있는 것과 먼저 고칠 것

조사 기준: 2026-10-28의 main(`api/planning.py`, `services/planning.py`, `services/workspace.py`, `services/taskmatch.py`,
`api/webhooks.py`, `app/models.py`).

### 3.1 그대로 쓸 수 있는 것

- 작업 지시 `BuildTask`(프로젝트별 번호, 상태 pending·in_progress·done·blocked)와 MCP 도구 — `list_tasks`·`update_task`·
  `submit_build_result`·`request_clarification`·`get_constraints`·`read_artifact`
- 커밋의 `task #N`으로 진행을 판정하는 `taskmatch`(기본 브랜치에 닿으면 done)
- 기본 브랜치가 아닌 push에 PR을 자동으로 여는 웹훅(머지는 사람이 Gitea에서)
- development 프로필 배포(`{프로젝트}~dev`) — 플래그 비교의 자리
- 코드 구조 분석 `codemap` — 항목이 닿는 범위 판정의 근거

### 3.2 개발 단계 전에 고칠 것

| 구멍 | 지금 | 개발 단계에서의 위험 |
|---|---|---|
| 담당자·선점 없음 | BuildTask에 담당자 필드·claim·잠금이 없다 | 두 Claude가 같은 항목을 구현한다 |
| 확정 = 자동 머지 | 기획 확정이 커밋 → PR → 바로 머지, 승인자 없음, 키만 있으면 누구나(`api/planning.py:448`) | 개발 단계가 기획 문서를 고칠 때 검토 없이 들어간다 |
| 덮어쓰기 확정 | 리포에 다른 내용이 있으면 "덮어쓸까요?" 뒤 overwrite | 나중에 한 쪽이 이기고 앞의 결정이 조용히 사라진다 |
| 워킹카피 공유 | 기획 확정이 `work_dir/{프로젝트}`(`workspace.workdir_for`)에서 브랜치를 바꿔 커밋 — **release 배포 폴더와 같다** | 동시 작업 시 checkout·reset이 겹치고, 떠 있는 앱의 폴더가 다른 브랜치로 바뀔 수 있다(추정, 재현 안 함) |
| 질의 전달 | `request_clarification`이 작업을 만든 세션이 아니라 **가장 최근 세션**으로 간다 | 질문이 엉뚱한 사람에게 간다 |
| 주인 없음 | 세션(ChatSession)에 만든 사람 필드가 없다(감사 로그로만 안다) | 요청자·결정권자를 정할 수 없다 |
| 조직 검사 | 세션 조회·확정·머지·삭제 API에 조직·프로젝트 접근 검사가 없다(화면이 거를 뿐) | 여러 부서가 쓰면 남의 프로젝트 세션을 고칠 수 있다 |
| 상충 검출 없음 | 프롬프트의 "앞 단계와 모순되지 말라" 한 줄뿐 | 충돌이 코드에서야 드러난다 |

## 4. 정할 것

1. **개발 단계의 자리** — 에이전트 기획의 6번째 단계인가, 프로젝트 화면의 별도 메뉴(개발 항목 목록)인가. 요청은 기획
   이후에도 계속 들어오므로 별도 메뉴를 권한다.
2. **Claude가 도는 곳** — 사람마다 PC의 Claude Code(MCP로 항목을 받는다)인가, 플랫폼이 Claude를 돌리는가. 선점·
   워킹카피·권한 설계가 달라진다.
3. **머지 권한** — 기획 안 항목을 검사 통과 시 자동 머지할지, 늘 사람이 머지할지.
4. **기능 플래그** — 대상 앱(사내 업무 앱)에 플래그를 개발원칙으로 강제해도 되는가. 안 되면 상충 항목은 결정 대기로만 처리한다.

넷이 정해지면 개발 항목의 데이터 구조(항목·상태·선점·결정)와 화면·MCP 도구 설계안을 만든다.
