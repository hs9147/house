# CHOFAM 생태계에서 paas의 위치

> paas 바깥에서 확정된 결정 중 paas에 해당하는 것을 정리한다. **결론부터: paas는 별건이며, 1차 구현 계획의 범위 밖이다.** 앞선 검토들이 paas를 배포 플랫폼으로 전제했다가 철회된 경위를 남긴다.
> **기준일:** 2026-08-05

---

## 1. 환경 C — 별건

CHOFAM 실행 환경이 셋으로 갈렸다.

| 환경 | 범위 | 1차 구현 |
|---|---|---|
| A | a_guild 단독 개발·테스트 | 아님 |
| **B** | society 계열 연동 (mentor·ethos·slime·society·terra) | **1차 목표** |
| **C** | **paas — 별건, 자체 호스트** | 아님 |

[1차 구현 계획](https://github.com/hs9147/chofam/blob/main/docs/implementation-plan-build.md)의 어느 Phase에도 paas 작업이 없다.

---

## 2. 경위 — paas를 배포 플랫폼으로 전제했다가 철회했다

앞선 검토들은 **paas가 CHOFAM 저장소들의 배포 플랫폼이 되는 구성**을 1안으로 다뤘다. 그 전제 위에서 여러 문서가 쓰였고, 전제가 바뀌면서 함께 무효가 됐다.

| 문서 | 지위 |
|---|---|
| chofam `paas-common-services.md` | **범위 밖** — paas가 구현할 공통 서비스 2건은 배포 플랫폼 전제 |
| chofam `compose-stack.md` §7 | **무효** — paas·a_guild·society를 한 호스트에 합산 |
| chofam `common-infrastructure-review.md` 1안 | 순서만 남고 배치는 대체됨 |

### 2.1 철회의 실질적 근거는 두 가지였다

**(1) paas가 상태 있는 서비스를 다루지 못한다.** `RuntimeSpec`에 볼륨·보안 옵션 필드가 없고, `DockerRuntime`의 컨테이너 생성 인자는 `image`·`name`·`detach`·`environment`·`ports`·`mem_limit`·`nano_cpus`·`restart_policy`·`labels`·`device_requests`로 한정된다. PostgreSQL 영속화와 a_guild 샌드박스의 보안 옵션(`read_only`·`cap_drop`·`internal` 네트워크)을 표현할 수 없다.

**(2) 계정 성격이 다르다.** paas `UserAccount`(`is_approved`·`is_admin`)는 운영자·관리자용이다. 계정 일원화 검토는 **내부 배포 콘솔 계정을 최종 사용자와 같은 발급자에 두면 권한 사고 표면이 커진다**는 이유로 paas를 분리 대상으로 뒀다. 이 판단은 지금도 유효하다.

**(1)은 paas의 결함이 아니라 범위다.** paas는 무상태 앱의 배포를 다루는 도구이고, 데이터 계층과 보안 경계를 표현하는 것은 애초의 목표가 아니었다. 그래서 "8개 필드를 paas에 구현한다"가 아니라 "compose로 운영한다"가 결론이 됐다.

---

## 3. 그래서 지금 paas는 무엇인가

**독립 제품이다.** 배포 플랫폼 역할을 전제한 요구사항이 사라졌으므로, paas는 자기 로드맵대로 진행한다.

| 항목 | 상태 |
|---|---|
| 배포 대상 저장소 | 없음 — B 환경은 compose로 직접 운영 |
| 공통 서비스 구현 요구 | **철회** |
| 계정 | **분리 유지** — 운영자·관리자용. 최종 사용자 발급자와 섞지 않는다 |
| A2A | 해당 없음 |

---

## 4. 다시 검토될 조건

paas가 배포 플랫폼으로 재론된다면 전제가 바뀌었을 때다.

| 조건 | 무엇이 바뀌어야 하는가 |
|---|---|
| 상태 있는 서비스 지원 | `RuntimeSpec`에 볼륨·보안 옵션. 실질적으로 K8s 런타임 성숙 |
| 다수 호스트 운영 | 단일 호스트에서는 compose가 더 단순하다 — paas의 이득은 호스트가 늘 때 나온다 |
| 배포 빈도 증가 | 지금은 저장소 5개, 저빈도. blue-green과 웹훅 자동 배포의 이득이 작다 |

**셋 중 어느 것도 1차 구현에서 발생하지 않는다.** 재론은 자체 서버가 여러 대가 되거나 실사용자 트래픽이 붙은 뒤다.

---

## 5. 정리

| 항목 | 상태 |
|---|---|
| 1차 구현 계획의 작업 | **없음** |
| 생태계 결정의 영향 | 배포 플랫폼 역할 요구가 **철회**됨 |
| 계정 | 분리 유지 (기존 판단 그대로) |
| 재론 시점 | 다수 호스트 운영이 필요해질 때 |

**paas는 자기 로드맵대로 진행하면 된다.** 다만 `macOS = 개발·데모용` 분류(`app/services/host.py`)는 자체 서버 하드웨어 검토에서 인용됐으므로, 그 판정이 바뀌면 chofam 쪽에 알린다.
