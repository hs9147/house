# 부서별 문서 저장소 전환

## 결정 사항

- 부서 간 상하관계와 공통/개별 저장소 유형은 없다. 저장소 하나는 한 부서에 속한다.
- 사용자에게 보이는 저장소 집합은 계정이 명시적으로 소속된 부서들의 저장소 합집합이다.
  미배정 저장소와 `internal`은 관리자만 접근한다. 일반 서비스 API 키에는 부서 소속이
  없으므로 문서 저장소 권한을 자동 부여하지 않는다.
- 저장소 등록 정보(이름, 원본 경로, 소속 부서, 읽기 전용 여부)는 플랫폼 DB가 단일 기준이다.
  `PAAS_DOC_ROOTS`와 `PAAS_DOC_ROOTS_READONLY`는 기존 설치의 최초 이관 때만 읽는다.
- 새 원본 경로는 `PAAS_DOC_ALLOWED_ROOTS`에 지정한 상위 디렉터리 안이어야 한다.
  값이 비면 새 저장소 등록을 막는다. 이름과 경로는 등록 후 API로 바꿀 수 없다.

## 온톨로지와 `.ready`

온톨로지와 검색 색인은 `PAAS_DOC_INDEX_DIR/<저장소 이름>.db`, LLM 읽기 캐시는
`PAAS_DOC_INDEX_DIR/.ready/<저장소 이름>/...`에 계속 둔다. 원본 파일 자체도 DB로
옮기지 않는다. 저장소 이름과 경로가 그대로인 레거시 항목은 기존 온톨로지 색인을 유지한다.
이전 버전의 `.ready` 문서는 원본 경로 해시가 없어서 첫 읽기에서 재추출된다. 그 뒤에는
크기·수정 시각과 원본 경로를 함께 확인한다.

조회·검색·재색인 대상은 DB에 등록된 활성 저장소이다. 파일 API, 온톨로지 API,
MCP 문서·그래프·저장소 서버, 스마트워크 도구에는 같은 부서 권한 필터를 적용한다.
여러 저장소 결과를 합칠 때도 각 결과의 `source`(저장소 이름)를 유지한다.

## 운영 이관 순서

1. 플랫폼 DB와 `PAAS_DOC_INDEX_DIR`을 백업한다. 원본 문서 폴더는 이동하지 않는다.
2. `PAAS_DOC_ALLOWED_ROOTS`를 새 저장소를 둘 상위 폴더로 설정한다. 여러 경로는
   세미콜론으로 구분한다.
3. 서비스를 새 코드로 재시작하기 전에 `python -m alembic upgrade head`를 적용한다.
4. 새 코드의 첫 기동에서 기존 `PAAS_DOC_ROOTS` 항목이 이름·경로·읽기 전용 상태를
   유지한 채 DB에 한 번만 등록된다. 이 시점에는 소속 부서가 없어 관리자만 볼 수 있다.
5. 파일 관리 화면에서 각 이관 저장소의 부서를 배정한다. 대표 사용자로 파일 목록,
   온톨로지, MCP 문서 검색을 확인하고 다른 부서 사용자에게는 404/빈 목록인지 확인한다.
6. 이후 저장소 추가는 DB 등록 화면에서 한다. `PAAS_DOC_ROOTS`를 변경해도 기존 DB
   목록은 바뀌지 않는다. 운영 확인 후 레거시 설정을 정리할 수 있다.

원본 경로를 바꿔야 할 때 기존 DB 행의 `root_path`를 직접 수정하지 않는다. 새 저장소를
등록하고 재색인·검증 후 전환한다. 직접 변경하면 기존 온톨로지 색인이 새 원본의 것으로
오인될 수 있다. `.ready`는 경로 해시로 낡은 캐시 사용을 막지만 온톨로지 색인은 저장소
이름을 기준으로 하므로 경로 변경을 자동으로 지원하지 않는다.
